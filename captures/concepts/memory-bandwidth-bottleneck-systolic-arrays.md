# Memory Bandwidth Is the Bottleneck Systolic Arrays Solve

## The problem every accelerator inherits

CPUs are designed to do everything — from rendering and operating systems to handling internet packets — so their superpower is managing unpredictability: a program might branch on user input or read a memory address known only at runtime, and CPUs dedicate much of their machinery to control logic that anticipates what comes next and recovers from wrong predictions. Neural networks barely need any of it; they mostly do one predictable thing over and over: matrix multiplication. In 2013 a small group of researchers at Google had built a speech recognition system that cut the error rate by 20% — the biggest jump in 20 years — but could not roll it out: with about 40 million parameters, close to AlexNet's 60 million, the projection still assumed ordinary CPUs would supply the compute, and Google simply did not have enough.

## The memory wall in numbers

The wall is physical. On the very first TPU circuit board, the die in the middle carries 28 megabytes of on-chip memory — static RAM, or SRAM — purely made of transistors and manufactured at the same time as the rest of the chip. But an SRAM cell requires six transistors and takes up a lot of space, so a chip can only fit so much of it. The two rows of black chips soldered onto the board are dynamic RAM: because it contains capacitors, DRAM is manufactured separately from the processor and sits about a centimeter away, connected by wires. That DDR3 generation is cheaper and 10 to 20 times smaller per bit than SRAM — which is why they could afford eight gigabytes of it. Before a model runs on the TPU, its weights are loaded into DRAM, and during inference the relevant weights must travel from external DRAM into the on-chip matrix multiply unit through the DRAM ports. That channel could carry only 34 billion bytes per second — the memory bandwidth. Imagine a naive version of the chip where each of its 65,000 MAC units fetches its own fresh weights on every clock cycle: at 700 megahertz that is a demand of 46 trillion bytes per second, three orders of magnitude more than the memory can deliver. In that naive world the processor would sit idle 99.9% of the time waiting for weights to arrive.

## Systolic arrays amortize the fetch

In 1945 John von Neumann proposed a new computer design: a processor that performs operations, separated from a memory that holds data and instructions, with a wire between them — the von Neumann architecture would power almost every computer built since. In 1977 John Backus, the inventor of Fortran, described it from the Turing Award stage as three parts: a central processing unit, a store, and a connecting tube that can transmit a single word between them. A few years later, in 1982, Professor H. T. Kung of Carnegie Mellon University published a paper that proposed a way around it. In a von Neumann architecture the processor performs one memory access per operation — fetch, compute, fetch, compute — and the cycle repeats. Kung's way out: do multiple operations for each fetch by reading a piece of data once and passing it through multiple processing elements before storing the result — amortizing the cost of memory access. The array of processing elements acts as a conveyor belt: on each clock cycle a new piece of data joins and moves through the pipeline at a constant rate. Kung was still a romantic: he imagined the memory as a pulsating heart whose contraction pushes blood through the organs, and named his invention after the systole — the systolic array.

## How the TPU applies it

The same idea powers Google TPUs, expanded from a vector into a grid. Each cell in the grid is a multiply-accumulate unit connected to its four neighbors — what Google calls the matrix multiply unit. The TPU uses a particular systolic array called weight-stationary: weights are streamed in through the north edge row by row and remain in place for the rest of the computation. Activations are transposed and their rows offset by one cell each, like a staircase; every clock cycle the block of activations shifts right one position, entering the top-left MAC unit where it multiplies by the stationary weight, and the product is added to a running sum arriving from the north edge (trivially zero at the top). Accumulated sums flow south while activations keep shifting right, and the sums that accumulate at the bottom of the grid are exactly the elements of the output matrix. The saving is concrete: one weight is brought from memory once but used once per activation in the batch, so weight traffic drops by a factor of B — the batch size. The trade-off is latency: to utilize TPU v1 at peak capacity Google has to use a batch size of 250, and gathering such a big batch from live traffic means the very first query waits much longer to be satisfied — a classic throughput-versus-latency trade.
